# Automatic evaluation preparation

Website, Apps Script and queue-maintenance code live on the website repository's `page` branch. The private evaluation runtime and all generated evaluation branches use `ZhaoRunyi/RoboSynChallenge_eval` **main** as their baseline.

The existing organizer service runs this entrypoint; no additional website server or agent is required:

```bash
python evaluation_tools/watch_preparation.py \
  --private-root /path/to/private/RoboSynChallenge_eval \
  --settings /path/to/private/prepare-settings.json
```

Use `--once` for one pass. Settings and credential files remain private (mode 0600), outside Git. The private checkout must be clean and on `main`.

Each pass checks legacy checkpoint source access independently of the still-required ten-task mapping, retries transient organizer transport failures with backoff, then invokes the existing queue preparer. Source access alone does not certify coverage of all ten tasks. Permission errors, missing model repositories and invalid policy trees remain visible for reviewer follow-up, not automatically guessed or repaired.

After each pass, `deadline-audit.json` beside the status file records the current per-request cutoff, selected commit, bundle and freeze status. `frozen` requires final code and all ten HF receipts, strictly pre-cutoff timestamps and matching prepared code. Legacy mappings, access failures and unfinished freezes remain distinct; they are never counted as complete. The file contains no credentials and is private (mode 0600). The audit is read-only; the existing preparer performs version selection, backup and reconciliation automatically.

Baseline changes rebuild already composed branches using the original pinned participant policy and checkpoint revisions. The backend backs up affected progress before invalidation; each current request keeps its canonical `eval_xxxx` branch. Installation uses the existing `rsc-prepare.service`, with this script as its ExecStart; after updating source or the unit, reload and restart the service.

## Issue reminders

Explicit organizer reminders can run without an agent:

```bash
python evaluation_tools/send_problem_reminders.py \
  --private-root /path/to/private/RoboSynChallenge_eval \
  --settings /path/to/private/prepare-settings.json \
  --deadline 2026-10-12T12:00:00Z \
  --batch /path/to/private/reminder-receipts.json
```

The deadline is UTC (the example means October 12, 20:00 Beijing time). The command rereads the latest request before each email, skips resolved issues, uses the standard backend template/button and activates a deadline-bound response round only after delivery. Reuse the same batch file for retries; `--retry-unrecorded` retries only absent or definitively rejected delivery records, never uncertain delivery.

After that deadline, rerun the same command with `--close` to send one closure reply to each confirmed reminder in its original Gmail thread. This explicitly expires that reminder's active link, preserves earlier corrections/progress, records the notice in Email status, and creates no new response link. Repeating `--close` skips confirmed deliveries; ambiguous sends require verification. Later follow-up is written by the assigned evaluator, not generated by an agent.

When MailApp's daily quota is exhausted, issue mail automatically uses the same organizer's Gmail API authorization. The Gmail advanced service is enabled in the manifest; existing Gmail scopes are reused. Gmail API/account limits still apply. A confirmed receipt stores the actual Gmail message ID for the workspace's email-history link. Ambiguous network failures require verification, not a fresh send ID.

## Participant confirmation drafts

This command audits backend identities, selected timestamps and remote branch manifests before generating private email drafts. It never sends mail, opens a correction link or changes evaluation progress.

```bash
python evaluation_tools/draft_participant_receipts.py \
  --private-root /path/to/private/RoboSynChallenge_eval \
  --settings /path/to/private/prepare-settings.json \
  --roster /path/to/private/approved-registrations.json \
  --output /path/to/private/participant-receipts
```

The roster is a bounded snapshot of approved `Users` records with `registrations` containing email, team, status and intended_use; exclude credentials. Drafts use one recipient per exact registered team name, preferring the latest eligible submitting account. Other registered contacts remain in the private review manifest, not CC. Explicit organizer test registrations are excluded; learning-only or other ambiguous registrations are retained for organizer review, not silently discarded. Teams with no request receive distinct text. Pending checks never become a false success confirmation. Review `version-audit.json`, `drafts.json` and `drafts.md` before any separately authorized mailing.

Send only after explicit organizer approval, using Gmail directly rather than Apps Script/MailApp. Keep one message per team with the existing HTML email shell; do not expose team addresses through shared To/CC lists. Store Gmail message IDs and ambiguous-delivery receipts privately. These notices create no response forms and do not change progress or admission deadlines.

## Completed Evaluation Protection

The website service installs `preparation_freeze.py` before loading the private
queue watcher. Once `workflow.stages[3].done` is true (stage four, uploads complete),
automatic preparation, retries and tool upgrades preserve its exact Git head,
bundle identity, checkpoint receipts, results, commands and progress. Stage five
is evidence review and is not required for this protection.

The same automatic-update protection applies earlier whenever code handoff
(stage two) is complete, or any current task result, upload session or reported
command exists. A machine may already be running a policy before its first
upload reaches the backend. These in-progress requests keep their existing
generation; a backward-compatible storage-tool PR does not authorize resetting
them. Only unused bundles are automatically recomposed. Explicit participant
corrections remain a separate versioning workflow.

Publication claims are held under the same backend lock as stage-four completion.
An update claims the current generation before composing or pushing; stage four
cannot complete during an unresolved publication. Successful registration releases
the claim. An uncertain push/registration reply retains its private operation ID
for retry, rather than allowing completion around an unregistered branch head.
Claims do not automatically expire into permission to complete stage four.
Automatic legacy branch retirement is disabled because its latest-request-only
inventory cannot safely classify historical completed branches.

Run the production entrypoint `evaluation_tools/watch_preparation.py`; the legacy
private CLI does not install this website policy. Do not run old one-off rollout
scripts alongside the service. Any manual reopening of completed evaluation data
requires a separate organizer decision; merging a main PR does not authorize it.

## Archive Pool Authorization

The current upload owner remains the ingress account. A second OneDrive account
must be authorized separately, not installed through `reviewer_configure_storage`:
that existing action replaces the single production upload owner.

After the organizer identifies and approves the destination account, forward SSH
port 53682 and run:

```bash
python evaluation_tools/authorize_archive_pool.py \
  --email NEW_ACCOUNT_EMAIL --slot onedrive-02 --probe-mib 100
```

To obtain authorization before approving any cloud file creation or testing, add
`--authorize-only`. This reads identity/quota and saves the pending credential
privately, then exits without creating a cloud folder or uploading/deleting files.
The ordinary command can resume this pending authorization after test approval.

`archive_pool_plan.py --queue PRIVATE_QUEUE.json --inventory PRIVATE_GRAPH.json`
performs read-only candidate selection from private snapshots. It accepts only one
completed upload and one submitted/checked result per task, paired ZIP/JSON files
under the expected `latest` directory, registered SHA256, and source item IDs,
eTags and sizes. It rejects ambiguous/incomplete records. A candidate is not a
verified copy: the worker must still recheck current registration/eTags and verify
the actual bytes before publishing a mapping or deleting anything.

Use the trusted preparer's Python environment, which already supports the existing
rclone authorization helper. The tool reads that helper from the private checkout;
it does not edit the checkout or any generated evaluation branch. Credentials and
the test receipt are written only under the Git-external private runtime directory.
The organizer signs into Microsoft in the browser; passwords, cookies, authorization
results and refresh tokens must not be pasted into chat. A mismatching account or
the current ingress drive is rejected. Only the dedicated destination folder and a
synthetic round-trip probe are created. The existing uploader is not reconfigured.

This tool stages authorization and verifies destination upload/download SHA256.
It does **not** enable migration or prove cross-account evidence transfer. Those
checks require the second account and are the next deployment gate.

The website-side worker processes each completed task, not an entire
evaluation request: copy its registered ZIP/JSON to a capacity-checked destination,
read back and verify the ZIP hash and JSON, publish a separately audited location
mapping, resolve evidence links using existing reviewer authentication, and only
then remove the unchanged source ZIP. Existing result manifests and their hashes
must remain intact. Uploading/unregistered files are never candidates. Failed
copies, verification or link publication retain the source and retry idempotently.

Do not use an account-wide recycle-bin cleanup. Ordinary Graph deletion moves
files into the recycle bin; capacity reclamation must be tested with synthetic
files first. Any permanent deletion must target only individually verified,
relocated evidence. Account tokens remain server-side. The long-running transfer
worker belongs to the website backend deployment, not to Apps Script request
execution or the participant evaluation runtime.

### Worker Deployment

Deploy `Reviewer.gs` and `ArchivePool.gs` through the selected-file deployment tool,
then publish the updated reviewer page. Account credentials stay in private runtime
files and backend Script Properties, never in public assets or evaluation branches.
Create a mode-0600 worker settings file with `api_url`, `organizer_email`,
`organizer_token_file`, optional `proxy`, and `cleanup_enabled` (default false).

```bash
python evaluation_tools/archive_pool_worker.py \
  --settings /path/to/private/archive-pool-settings.json \
  --pool-root /path/to/private/archive-pool \
  --source-owner /path/to/private/onedrive-owner.json --once
```

`--once` processes one smallest eligible task for canary verification. The default
long-running mode uses two bounded workers (`--workers 1..4`) and polls every 20
seconds while transfers run. Each task has independent HTTP sessions. Account
capacity and disk spool space are reserved before dispatch, with a 2-GiB safety
margin; unprobed accounts and duplicate drive identities are excluded. Failed
accounts do not prevent use of healthy accounts. Failed tasks retry with backoff.
Private temporary spools are removed after each task and on graceful shutdown.

Enable source cleanup only after the canary and frontend links pass: an admin must
call `reviewer_archive_pool_enable_cleanup` with `enabled:true` and an explicit
approval reason, and set `cleanup_enabled:true` in the private worker settings.
Both gates are required. Cleanup permanently removes only the exact unchanged
source ZIP under the configured ingress root. It never empties the recycle bin.
The tiny original `result.json` stays at ingress so existing upload retries remain
compatible. The immutable original manifest, command, result and SHA256 remain
unchanged; a separate append-only location record supplies navigation.

Install `rsc-archive-pool.service` in the trusted host's user systemd directory and
enable it for restart recovery. The template uses the existing workspace and
Python environment. The service discovers new successfully probed pool slots on
the next poll without a restart. OAuth refresh is automatic while the grant is
valid; revoked consent or a new tenant login requirement still requires the owner.

The private settings are reloaded on every coordinator poll. Optional integer
settings are `workers` (1-4, default 2), `reserve_gib` (1-1024, default 2),
`poll_seconds` (10-3600, default 20), and `retry_seconds` (10-86400, default 120).
Reducing concurrency lets current jobs finish without admitting excess new jobs.
Connection/proxy changes wait for current jobs to drain; each job retains its own
connection snapshot. Invalid settings stop new dispatch and disable local cleanup.
`cleanup_enabled` is checked again immediately before deletion, not just when a
transfer starts. The independent backend cleanup approval must also remain enabled.
Adding verified accounts, refreshing credentials, discovering uploads, retrying,
publishing navigation and approved cleanup require no manual service restart.

Admin APIs `reviewer_archive_pool_status` and `reviewer_archive_pool_queue` expose
service status and current registered candidates without account tokens. Local
`worker-status.json` and the systemd journal record transfer phases. The reviewer
page resolves evidence through the authenticated backend; its task links point to
the reviewer workspace, not to a stale OneDrive URL. Historical raw OneDrive URLs
in original manifests are not cloud-provider redirects and must not be used as
the relocated archive's canonical navigation link.
